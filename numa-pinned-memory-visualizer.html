Keep memory close to the CPU, close to the GPU

On a multi-socket server, a training step is only as fast as the path your data takes: RAM → CPU → GPU. See what happens when that path stays inside one NUMA node — and when it doesn’t — plus why pinned (page-locked) memory makes the final hop 2–3× faster.

What “NUMA” actually looks like inside the box

04 — figure 3-5, animated

Pinned vs pageable memory: the H2D copy race

Regular (pageable) memory can be swapped or moved by the OS, so the GPU can’t DMA from it directly — the runtime secretly copies it through a pinned staging buffer first. Pinned memory skips that step.

🟩 pinned (page-locked) RAM — pin_memory=True idle
🟧 ordinary pageable RAM idle
why pinned wins
  • OS can’t swap or move page-locked memory → the GPU (or NIC) can DMA directly from it.
  • Host→device copies can be 2–3× faster than from pageable memory.
  • cudaMemcpyAsync genuinely overlaps the copy with GPU compute (no hidden sync).
why pageable loses
  • DMA can’t touch memory the OS might relocate → runtime copies through a pinned staging buffer (extra CPU copy).
  • Extra synchronization reduces overlap of copies with GPU work.
  • Biggest penalty with large batch sizes or when H2D copies are on the critical path.

05 — put it into practice

pin_memory=True — and the limit that can bite you

Frameworks expose pinning as a one-liner. But the OS caps how much memory a user may lock (ulimit -l) — ask for more pinned memory than the cap allows and the allocation fails.

# PyTorch DataLoader — batches land in page-locked (pinned) RAM
loader = DataLoader(dataset,
                 batch_size=256,
                 num_workers=4,   # fork-based → inherits NUMA policy
                 pin_memory=True) # ← the flag that matters

for x, y in loader:
    x = x.to("cuda", non_blocking=True) # fast async DMA
Pinned memory + non_blocking=True lets the H2D copy overlap with GPU compute — most visible with large batches or when copies sit on the critical path.
pinned buffers you want (DataLoader, caches…)

# raise the cap
$ ulimit -l unlimited
# docker: adjust the container’s limits
$ docker run --ulimit memlock=-1 …
# k8s: raise memlock in the securityContext
Rules of thumb: keep memory, process and GPU on one NUMA node (numactl --cpunodebind=N --membind=N, fork-based workers) · set pin_memory=True on data loaders · enable GPUDirect RDMA / GDS on supported hardware · set ulimit -l (memlock) to unlimited for AI/HPC workloads.

The report card after launch: numa_hit = memory served by the right node. A growing numa_miss means remote traffic — your binding isn’t doing its job. Re-check after any scheduler or config change.

⚠️ Gotchas worth knowing

  • --membind is strict — if that node’s RAM runs out, allocation simply fails (OOM). --preferred is the forgiving sibling: try node 1 first, quietly fall back elsewhere. Start with --preferred, graduate to --membind once you trust the setup.
  • taskset / docker --cpuset-cpus bind CPU only — memory still follows first-touch. Pair them with --cpuset-mems (or numactl --membind) for the memory half of the policy.
  • Python ≥ 3.14 gotcha: the POSIX default multiprocessing start method changed from fork to forkserver — newly launched DataLoader workers may silently stop inheriting your NUMA policies. Set the start method explicitly (mp.get_context("fork") for CPU-only workers) or re-apply the policy inside each worker.
  • GPUDirect doesn’t configure itself: RDMA needs the nvidia-peermem kernel module loaded; GDS rides on the cuFile API + nvidia-fs driver. Verify they exist in your container image before counting on direct paths.
  • Pinned memory is a budget, not a free lunch — pinned pages can never be swapped or used by anything else on the host. Size DataLoader buffers deliberately, and keep ulimit -l above that budget (section ⑤).
mini-glossary

Words this section keeps using

NUMA node — a CPU socket + its local RAM + its PCIe devices. Access is fast inside, slow across.
first-touch policy — memory is allocated from the node of the CPU that first touches it (where the thread runs).
UPI — Ultra Path Interconnect; the glue between sockets. Every cross-node hop pays latency.
pinned / page-locked memory — host RAM the OS promises never to swap or move; DMA-friendly.
pageable memory — ordinary malloc’d RAM; can be moved, so DMA needs a staging copy.
DMA — direct memory access; a device moves data without the CPU touching each byte.
H2D / D2H — host-to-device / device-to-host copies over PCIe.
GPUDirect RDMA — NIC (e.g. InfiniBand) reads/writes GPU memory directly.
GPUDirect Storage (GDS) — NVMe streams data straight into GPU memory.
memlock — the OS limit on how much memory a user may pin (ulimit -l / docker --ulimit memlock).
node distance — numactl’s relative cost of memory access: local = 10, remote often 21 ⇒ ≈2.1×.
numa_hit / numa_miss — numastat counters: allocations served by the right vs wrong node.
NVLink — NVIDIA’s GPU↔GPU interconnect; shows up as NV# in nvidia-smi topo -m.
